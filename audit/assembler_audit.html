Assembler audit: versions, upgrade room, and the right tool per kingdom

EGAP builds a genome by running several on the same reads and keeping the best result. This audit checks how old those assemblers are, what stops us upgrading them, whether newer tools win for specific kinds of organism, and which organisms we would need to test them fairly.

Summary

Your plan makes sense, and the audit found six things

Making a separate branch, raising the version , and comparing old and new images with an is the right way to do this. Three findings change how that branch should be set up.

  • Blocker
    Python 3.8 is what holds EGAP back, not the assemblers. The is pinned to Python 3.8. Flye 2.9.6, compleasm 0.2.9+, BUSCO 6 and most of the newer bacterial tools publish no Python 3.8 build. The upgrade branch has to move to Python 3.10 first, and the pandas/numpy pins will have to move with it.

    Update: done, on Python 3.12, since 3.10 reaches end of life in October 2026. The only real blocker was a stale pin in compleasm's recipe, worked around in EGAP and reported upstream.

  • Test data
    The three E. coli read sets are three different strains, and none of them is K-12. The reference is K-12 MG1655 (GCA_000005845.2). The PacBio reads are O157:H7, which has a genome about 0.8 Mb bigger. Comparing against the wrong reference makes error counts meaningless. An A/B test needs reads and a reference from the same strain.

    Update: the A/B tests added K. pneumoniae KPC2_202310: nanopore reads, Illumina reads and a complete reference, all from one isolate. Every accuracy number in the results comes from it.

  • Wrong comment
    The Dockerfile's reason for pinning Flye is not true. Line 41 says ">=3.0 changes assembly graph format". Flye 3.0 does not exist; the newest release is 2.9.6. The real reason to stay on 2.9.5 is that 2.9.6 has no Python 3.8 build.

    Update: comment corrected, and EGAP now uses Flye 2.9.6.

  • Versions
    Only two assemblers have newer releases. SPAdes 4.3.0 is a straightforward bump. Flye 2.9.6 is a small fix release, but it changes the default for nanopore R10 reads. MaSuRCA 4.1.4 and hifiasm 0.25.0 are already the newest releases. RagTag 2.1.1 fixes a wrong-orientation bug but is not on Bioconda yet.

    Update: SPAdes 4.3.0, Flye 2.9.6, BUSCO 6.1.0 and compleasm 0.2.10 are in. None of them changed an assembly's quality.

  • Per kingdom
    The read type matters more than the kingdom, but there are clear winners. For animals and plants, use hifiasm, including its newer nanopore mode. For fungi, use Flye plus short-read . For bacteria and archaea, build an Autocycler . Long-read-first assembly has overtaken hybrid assemblers like MaSuRCA in every recent benchmark we found.

    Update: the bacterial A/B agreed. Polypolish + Pypolca beat Pilon, and Racon stayed ahead of Medaka.

  • Our own runs
    On the nanopore + Illumina E. coli test, Flye and MaSuRCA did badly. They recovered 75% and 49% of the genes, while SPAdes recovered 99.7%. The raw nanopore data covers the genome hundreds of times over, so low doesn't explain it. Diagnose this before blaming the versions.

    Update: those June numbers predate two fixes already on main: the hybrid sample re-paired with Illumina reads from the same isolate, and Flye's nanopore mode chosen from the reads. In every A/B run on current main, Flye scored 99.7% and MaSuRCA 99.1–99.4%.

The plasmid problem, and the replicon check

The first full run with the new defaults picked Flye-mode MaSuRCA for K. pneumoniae, because it had the fewest . But it was missing the reference's 13.8 kb . EGAP's scoring (BUSCO, contig count, N50) can't see a lost , so it rewarded the loss.

EGAP now aligns every assembly against every other. For bacteria and archaea, it rules out an assembly that lacks a contig of at least 5 kb that two other assemblers both made. With no reference, it leans towards keeping plasmids: the assembly must hold 95% of such a contig, not just half. On both hybrid test samples this rules out Flye-mode MaSuRCA, so the final choice goes back to the assembly that keeps every plasmid.

Bugs the tests uncovered

  • FastQC never ran in the shipped image. Conda installed FastQC 0.13, which rejects the -o flag EGAP used, so read-QC reports were silently missing.
  • The full Docker image ran tools with the wrong Python. Funannotate failed outright, and EGAP picked up the annotation environment's Trimmomatic.
  • The annotation environment's install hung for 7+ hours. It now solves in under a minute.
  • MaSuRCA's Flye mode passed an option only Flye 2.5 understood. EGAP now filters it out, and the Bioconda recipe fix is in bioconda-recipes #70313.

Still open

  • The Bioconda release on Python 3.12 waits on compleasm's recipe fix (#60482). Update 2026-10-28: merged as #70268; compleasm is back in the conda installs.
  • All accuracy evidence comes from one bacterium. A plasmid-rich hybrid with a same-strain reference, and one test organism per kingdom (see Test organisms), would strengthen it.
How EGAP assembles today

Which assembler runs for which reads

EGAP looks at the reads in each row of the input table and runs every assembler that can use them. It then scores each result on BUSCO/compleasm completeness, count and , and keeps the best one. These rules come from bin/assemble_*.py.

Flye's PacBio mode is always --pacbio-corr (assemble_flye.py:146). That is the mode for pre-corrected long reads. Flye has a dedicated --pacbio-hifi mode for reads, which suits them better. This is a small fix for the new branch.

hifiasm runs on any PacBio input, but it is built for HiFi reads. On older data it can give poor results. EGAP already calculates HiFi read statistics, so it could skip hifiasm when the reads are not HiFi.

What blocks upgrades

The Python 3.8 wall

Conda installs every tool into one environment, and each tool's package says which Python versions it supports. EGAP's environment is fixed at Python 3.8, which reached end of life in October 2024. More and more packages no longer publish 3.8 builds, so conda quietly settles on an older version or refuses to install.

ToolNewestNewest on Python 3.8Blocked?

Consequence for the branch: step one is python>=3.10,<3.13, and then the pandas/numpy pins it frees up (the Dockerfile notes that pandas 2.0.3 is the last 3.8 build). Medaka 2.2 needs Python 3.12, and Verkko and Hybracter are pipelines with many dependencies. These three belong in a separate side environment, the same way funannotate_env is already separate.

Why this matters for an A/B test

The reference genome, GCA_000005845.2, is K-12 MG1655 at 4,641,652 bp. The PacBio assemblies come out at about 5.4 Mb because O157:H7 really is bigger. That is correct biology, but QUAST counts it as errors against K-12.

The Illumina test's final assembly is exactly 4,641,652 bp in 1 contig, the length of the reference itself. RagTag ordered the contigs along K-12 and filled the gaps with s. That is fine for a smoke test, but it hides real assembly differences between two versions.

The nanopore + Illumina pair is a good pair: same strain, about 700× nanopore coverage. It has no matching finished reference, though.

What it costs to run these

Archaea, bacteria and yeast (2–15 Mb) finish in minutes with under 8 GB of RAM, so they can run in full on every A/B run.

Arabidopsis, C. elegans and Drosophila (100–145 Mb) need first. At 30× HiFi, hifiasm takes about 8–15 GB and 20–60 minutes. Short-read SPAdes or MaSuRCA at 50× needs 30–50 GB, which is close to the 55 GB limit.

These are the research agent's estimates from typical tool behaviour, not EGAP measurements. Round 1 of the A/B plan would measure them.

Original proposal · carried out, see A/B results

How an upgrade branch would be A/B tested

This is the plan as written before the tests. It was followed, with two changes: Python went to 3.12 instead of 3.10, and new tools came in as tested replacements (Polypolish, Pypolca, MaSuRCA's Flye mode), not in a side environment.

This reuses the existing k3d A/B harness in tests/ab/ab-test.yaml. It runs the same samples under the same CPU and RAM limits, with egap:old against egap:new.

  1. Fix the test data first. Use read sets and references from the same strain, for example K. pneumoniae KPC2_202310 for bacteria and one primary organism per kingdom from the table above. Otherwise QUAST's misassembly and error counts can't tell old and new apart.
  2. Branch chore/assembler-refresh from main. Move the env to Python 3.10, then raise the pins in Dockerfile and meta.yaml together: SPAdes 4.3.0, Flye 2.9.6, compleasm 0.2.10, BUSCO 6.1, and RagTag 2.1.1 once it reaches Bioconda. Correct the Flye comment.
  3. Change one thing per round. Round 1 changes only Python and the dependencies, and its output should match the old image exactly. Round 2 changes the assembler versions. Round 3 adds new assemblers (hifiasm --ont, Flye --pacbio-hifi). That way any difference can be traced to a single cause.
  4. Decide pass or fail in advance. For each sample the new image must keep BUSCO/compleasm completeness within 0.5 points, must not increase QUAST misassemblies or per 100 kb against the same-strain reference, and must stay within 125% of the old runtime and peak RAM.
  5. Treat completeness tools separately. BUSCO 6 and compleasm 0.2.10 with odb12 lineages change the measuring stick itself. Score both images with the same BUSCO version, or the comparison is unfair.
  6. Add the new assemblers in a side env (Autocycler, Medaka/Dorado, Verkko). That keeps EGAP_env installable and limits the Python fallout.
